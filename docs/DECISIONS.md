# Decisions

Resolved deviations and clarifications of `docs/vitalsshield_technical_architecture_specification.md`. Notes and
reports cite these by number ("DECISIONS #23").

| # | Spec section | Resolution |
| :--- | :--- | :--- |
| 1 | §4, §6 | Quarantine allowed from ACTIVE or REAUTH_REQUIRED; revokes all non-revoked certs (KEY_COMPROMISE), evicts, then sanitizes. |
| 2 | §3 | Server TLS Issuing CA under Root (EKU serverAuth) issues the gateway cert; simulator trusts Root; Device Intermediate stays clientAuth-only. |
| 3 | §4, §8 | Live Protocol A includes the Key #4 DEK anchor. Since Phase 6, passkey_registry_kms_sig and Signer-side re-verification of the provisioning assertion are live too (rows 56 and 57); in bearer mode (row 60) neither applies. |
| 4 | §4, §7 | Admin API: setup code at first boot; POST /admin/passkeys, /admin/devices (begin/finish), /admin/assignments, /admin/assignments/{id}/close, /admin/devices/{id}/restore-active, /admin/devices/{id}/quarantine. |

| 12 | §3 | Local reconciliation is all-or-nothing over four keys; old ca_issuers REVOKED, never deleted; leaves revoked (HIERARCHY_REBUILD); devices reset; trust file rewritten after commit. |
| 13 | §4, §8 | If the eviction backstop poller is not built, §4 and §8 mark it "Designed". |

| 15 | §3 | Gateway TLS private key is ephemeral, in memory, regenerated each boot; 24 h cert from the Server TLS CA; the one key outside KMS. |
| 16 | §3 | Boot order: Flyway, reconcile, gateway TLS, trust anchors, deny-list seed, CRLs published, bind listeners. |
| 17 | §3 | KMS signing uses MessageType DIGEST; RAW caps messages at 4096 bytes, which a CRL passes at about 100 entries. |
| 18 | §3 | SKI = SHA-256 of SPKI DER (RFC 7093 §2 method 4). |
| 19 | §3, §7 | App revocation reasons map to RFC 5280 CRLReason; unspecified omits the extension. |
| 20 | §3 | Rebuild keeps QUARANTINED/DECOMMISSIONED trust states; DEK cleared for all. |
| 21 | §4 | Protocol C nonce fixed at 16 bytes. |
| 22 | §7 | ca_issuers lacks revocation metadata; root CRL derived; production gap. |
| 23 | §4 | CertStatusResolver has no 5 s cache; DB lookup per request on boundedElastic. |
| 24 | §4 | Handshake uses an in-memory deny-list (with deniedFrom), not an accepted-status lookup; post-handshake gate checks every completed handshake, including resumed ones. |
| 25 | §1, §8 | All listeners bind 127.0.0.1 by default; admin always loopback. |
| 26 | §2 | TLS resumption prevented by invalidating each server session after the handshake check (the JDK ticket property alone left cache-based resumption on). Observed (Phase 2.1, JDK 21.0.13, OpenSSL 3.6.4 s_client): the server still sends one NewSessionTicket per connection, but a client presenting it gets a full handshake ("New", never "Reused"); after revoke that full handshake is refused by the trust manager (alert 46, certificate unknown). |
| 27 | §4 | CRLs cached and republished on revocation and before nextUpdate; HTTP GET never signs. |
| 28 | §4 | The 30 s deny-list refresh is a backstop for the handshake deny-list. It is not the spec's 3 s eviction poller (still a Phase 9 stretch) or Redis (Designed). |
| 29 | §4 | The CRL endpoint has no rate limit. Production publishes CRLs to object storage behind a CDN and rate-limits 8444 at the L4 load balancer. "Designed". |
| 30 | §4 | Each gateway process caches its own CRL. With multiple gateways the CRL Number can briefly differ between them (it still always increases). Production publishes one CRL to shared storage. "Designed". |
| 31 | §4 | Protocol A defines a "first-time device" as one with no prior certificates row. Such a device keeps boot_epoch = 1; any other device gets boot_epoch + 1. provisioned_at cannot be used because hierarchy rebuilds reset it. |
| 32 | §4, §8 | Until Phase 6, a dev seed tool creates the device, the ACTIVE assignment, and the bootstrap token. Its WebAuthn fields are visibly fake (DEV-SEED-NOT-WEBAUTHN). It runs as a Gradle task from the test classpath, refuses any database other than the local Compose database, and is never an HTTP endpoint. |
| 33 | §3, §4 | Signatures outside JWS (DEK proofs, KMS anchors) are DER ECDSA. Only JWS uses raw R\|\|S. |
| 34 | §4 | Enrollment token semantics: a cryptographic or proof failure revokes the token (fail closed); a transient KMS or DB failure returns it to ISSUED; a token stuck in CLAIMING for more than 2 minutes can be claimed again. |
| 35 | §4, §5 | certificates.cert_thumbprint_s256 stores base64url(SHA-256(cert DER)), 43 characters, which is exactly the JWS x5t#S256 value. |
| 36 | §4 | The simulator uses 127.0.0.1 URLs (the gateway cert has an IP SAN) with hostname verification on. |
| 37 | §2 | Deny-listed certs fail with a CertPathValidatorException(REVOKED) cause, and validity failures keep their EXPIRED cause, so JSSE can send alerts 44 and 45. Observed (Phase 3, JDK 21.0.13): the server still sends alert 46 (certificate_unknown) for every rejected client certificate. JDK 21 `sun.security.ssl.CertificateMessage.checkClientCerts` (TLS 1.2 and 1.3 paths) always calls `fatal(Alert.CERTIFICATE_UNKNOWN, ce)`; the cause-to-alert mapping (`getCertificateAlert`) is used only when a client checks a server. The cause chain is kept (harmless; a future JDK or another provider may use it). |
| 38 | §3, §4 | Serial reservation ledger: every device leaf serial is reserved in issued_serials (RESERVED) inside the same short transaction that claims the token, before any KMS call. Activation marks it RECORDED. An aborted activation marks it VOIDED and, if the signed leaf is in hand, stores it in certificates as REVOKED (REPLACED_BEFORE_USE) and deny-lists it. A sweep at boot and on every stale reclaim voids RESERVED serials older than 2 minutes. CRLs list REVOKED certificates plus VOIDED serials (reason superseded), so every device serial the CA ever signed is either recorded or revocable, even when the certificate itself was lost. |
| 39 | §3 | Gateway leaves (Server TLS CA) are not tracked in issued_serials, and the Server TLS CA publishes no CRL. Each gateway leaf lives 24 h and its key never leaves JVM memory. A Server TLS CA CRL is "Designed". |
| 40 | §5 | Sequence numbers start at 1; a sequence_number below 1 is rejected. |
| 41 | §4, §8 | Until Phase 6, /api/v1/admin/** (except boot-status) requires the boot-generated setup code as a bearer token. The code is written to var/admin/setup-code (permissions 600) and never printed or logged; only its path is logged. This is also the fallback if WebAuthn is cut. |
| 42 | §6 | Quarantine locks the devices row FOR UPDATE and sets QUARANTINED before running the sanitize CTE as a separate statement in the same READ COMMITTED transaction, so an in-flight ingest cannot commit an ACCEPTED row after the quarantine. |
| 43 | §5 | JWS header policy: alg must be ES256; typ must be vitalsshield.telemetry+jws; x5t#S256 is required; jwk, jku, x5c, x5u, and crit are rejected. The verification key comes only from the TLS client certificate. Unknown payload fields are rejected. |
| 44 | §5, §8 | Simulator offline handling is simplified: it retries the same frame (same batch_id and sequence number) until it succeeds. The flash ring buffer stays "Designed". |
| 45 | §4 | Quarantine also revokes the device's outstanding ISSUED and CLAIMING bootstrap tokens. |
| 46 | §6 | Phase 4 classifies telemetry by plausibility bounds and perfusion only (REJECTED_IMPLAUSIBLE, SIGNAL_DEGRADED, ACCEPTED). Activity context, acute thresholds, calibration, drift, and alerts arrive in Phase 7. |
| 47 | §8 | Dashboard: Next.js static export served on the admin port from a filesystem directory (vitalsshield.dashboard.dir, default dashboard/out). The operator pastes the admin setup code at sign-in; it is held in sessionStorage until Phase 6 adds WebAuthn. |
| 48 | §8 | The dashboard polls every 500 ms instead of using SSE: EventSource cannot send an Authorization header. |
| 49 | §3 | KMS health monitor: DescribeKey on the four ACTIVE keys every 30 s. It reports and alarms but never rebuilds at runtime; recovery means restarting the server, which rebuilds and revokes every device. |
| 50 | §8 | Serials are displayed as uppercase whole-byte hex, the way `openssl x509 -serial` and `openssl crl -text` print them. The stored format is unchanged. |
| 51 | §8 | Devices and tokens created by the dev seed tool show a visible DEV SEED badge on the dashboard. |
| 52 | §8 | The Next.js 16 static export contains inline scripts (3 in index.html, including the `_R_` hydration bootstrap), so `script-src 'self'` alone breaks it. Instead of `'unsafe-inline'`, the dashboard handler adds the SHA-256 hash of every inline script in the served HTML file to `script-src` (computed at serve time, cached per file and modification time). External scripts are still `'self'` only. |
| 53 | §8 | npm audit reports moderate advisories only in dashboard lint tooling (minimatch under typescript-eslint); production dependencies have 0. Accepted for the hackathon; no audit fix mid-build. Re-check before any deployment. |
| 54 | §1 | WebAuthn library: Yubico java-webauthn-server (webauthn-server-core 2.10.1, Java 8+ so Java 21 is fine). Its Jackson 2 stays internal: runtime scope only, plus `jackson-core` as compileOnly so javac can see a declared JsonProcessingException; NoJackson2ImportsTest fails the build if an app class imports com.fasterxml.jackson outside the annotations. |
| 55 | §1, §8 | The admin plane is served at http://localhost:8445 (WebAuthn RP ID "localhost"; an IP address cannot be an RP ID). The admin listener binds 127.0.0.1 and ::1. A GET for an HTML page with Host 127.0.0.1 gets a 307 redirect to http://localhost:8445. |
| 56 | §2, §3 | Passkey registry anchor is live: on registration, KMS Key #4 signs PasskeyAnchorBytes (encoding 1); the anchor is verified before every assertion against that credential. |
| 57 | §2, §4 | Protocol A re-verifies the clinician's stored WebAuthn assertion (signature, challenge == recomputed ProvisioningDigest, rpIdHash, UP and UV flags, origin) after verifying the passkey anchor. A token row without a valid assertion cannot enroll. The dev seed tool now uses a registered software passkey, so its tokens pass the same verification and keep the DEV SEED badge. |
| 58 | §4 | Step-up approvals bound to the action: quarantine and restore-active each require a fresh assertion whose challenge is SHA-256 of a canonical action encoding (purpose, device_id, parameters, 16-byte server nonce). Parameters are held server-side between begin and finish; finish accepts only the assertion. |
| 59 | §1 | Admin session: random 32-byte id, cookie HttpOnly, SameSite=Strict, Path=/api/v1/admin, no Secure flag (plain HTTP on loopback), in memory, 30 min idle and 8 h absolute. Every non-GET admin request must carry an Origin header equal to an allowed origin. |
| 60 | §1, §8 | After Phase 6 the setup-code bearer only authorizes registering the FIRST passkey (when zero passkeys exist). Everything else needs a passkey session, and quarantine/restore need step-up. scripts/demo-cli.sh defaults to UI quarantine mode. |
| 61 | §1 | Signature counter: 0 is always accepted (synced platform passkeys report 0); a non-zero counter must be strictly greater than the stored value, else the assertion is rejected and logged. |
| 62 | §7 | security_audit_log hash chain (should-have): entries for PASSKEY_REGISTERED, DEVICE_PROVISIONED, ASSIGNMENT_CREATED, ASSIGNMENT_CLOSED, DEVICE_QUARANTINED, DEVICE_RESTORED, each with actor clinician_id and the SHA-256 of the approving assertion, chained under pg_advisory_xact_lock. S3 Object Lock anchoring stays "Designed". |
| 63 | §1 | Attestation conveyance "none": registration trusts the authenticated session or setup code, not the authenticator model. Attestation verification is "Designed". |
| 64 | §1, §8 | Two Phase 6 rules around the dev seed tool and tests. (a) "Zero passkeys" for the first-registration rule counts clinician passkeys only: the dev seed software passkey (clinician dev-seed-clinician) is excluded, so seeding a demo device never locks out the first real Touch ID registration. (b) Phase 2 to 5 integration tests run in bearer mode (TestPorts.register), the behavior they assert; Phase 6 tests and the e2e tier run in webauthn mode. |
| 65 | §4, §8 | Ceremony details. Sign-in and registration ceremonies are keyed by their challenge (the finish body is just {credential}); provisioning and step-up ceremonies by a random ceremony_id. Any unknown, used, or expired ceremony is 410 CEREMONY_EXPIRED. Quarantine's audit entry is written in its own short transaction right after the Phase 4 quarantine commits (the quarantine runs its own transactions). A PROVISIONING_UNVERIFIED refusal voids the reserved serial without republishing the CRL, so the refusal makes no KMS Sign call (the serial was never signed; it joins the CRL at the next republication). webauthn_* token columns hold base64url of the exact signed bytes. |
| 66 | §1, §2 | The dev seed passkey is restricted (Phase 6.1). Migration V4 adds clinician_passkeys.purpose (CLINICIAN default, or DEV_SEED); V4 backfills the dev seed rows written before the column existed, and from then on the seed tool writes DEV_SEED itself and runtime checks read only the column. A DEV_SEED credential may only finish provisioning ceremonies begun by the seed tool's code path (ProvisioningService.beginForSeedTool, which no HTTP route calls), and only when the active profile is local (DevSeedPolicy). It is refused, before any state changes, for session sign-in and every step-up (403 DEV_SEED_NOT_ALLOWED); outside local, every DEV_SEED assertion is refused, Protocol A refuses tokens it approved, and the seed tool refuses to run. Assignment close is session-only, so a DEV_SEED credential cannot reach it. The first-passkey count and the dashboard's DEV SEED badge use purpose. |
| 67 | §7 | Audit entries are atomic with the action they record: DEVICE_QUARANTINED is appended inside the quarantine transaction (after the row lock, state flip, token revocation, and sanitize CTE); restore, provisioning, registration, and assignment changes already append in their own action's transaction. Lock ordering rule: every transaction that appends to security_audit_log takes pg_advisory_xact_lock last, after all row locks it needs, so a holder of the audit lock never waits for a row lock and no wait cycle can form. The certificate revocation that precedes the quarantine transaction is not rolled back if that transaction fails (fail closed). |
| 68 | §6 | Clinical streak state lives on patient_device_assignments (resting_since, degraded_critical_streak, drift_breach_streak). telemetry_records gains activity_context (RESTING\|EXERTION, nullable) and clinical_evaluated_at. clinical_alerts gains condition_code. All added in V5. |
| 69 | §6 | Clinical evaluation runs after the ingest CTE commits, in its own transaction. "Consecutive" and "sustained" are judged in ingestion order per assignment. If measured_at goes backwards relative to the previous evaluated batch, resting_since resets. |
| 70 | §4, §6 | Global lock order: devices (FOR KEY SHARE in clinical evaluation, FOR UPDATE in quarantine) -> telemetry_records -> patient_device_assignments -> clinical_alerts -> audit advisory lock last. The evaluator locks the assignment row FOR NO KEY UPDATE, the lock its own UPDATE of non-key columns takes anyway: it still serializes evaluators and the quarantine CTE's UPDATE, but does not block the FK key-share lock that an ingest INSERT takes on the same assignment row. |
| 71 | §6 | Alert dedupe: LOW_PERFUSION_CRITICAL_ALERT fires when its streak reaches 3, then not again until the streak resets. ACUTE_PHYSIOLOGICAL_ALERT is suppressed if an ACTIVE or ACKNOWLEDGED alert with the same assignment and condition_code has a triggering batch measured within the last 5 minutes. POTENTIAL_PHYSIOLOGICAL_DRIFT fires when its streak reaches 4 and resets the streak. |
| 72 | §6 | Calibration uses only ACCEPTED RESTING batches that did not trigger an acute alert. Statistics: sample mean and sample SD (n-1), with SD floors HR 3.0 bpm, HRV 5.0 ms, SpO2 1.0 pct (Phase 8; Phase 7 used 1.0, 1.0 and 0.5, which let a tight demo calibration turn ordinary noise into z-scores near 9). Window size vitalsshield.clinical.calibration-size: 30 by default, 10 in the demo profile. |
| 73 | §6 | The drift streak counts only ACCEPTED RESTING batches on a LOCKED baseline. EXERTION and SIGNAL_DEGRADED batches neither count nor reset it; a non-breaching RESTING batch resets it. |
| 74 | §6, §8 | Refines 6: the simulator persists its last measured_at and continues from max(last + 60 s, now - 12 h), capped at server time, instead of recomputing the offset on each launch. Scenarios can be switched live. |
| 75 | §7 | security_audit_log is append-only at the database level: a trigger rejects UPDATE and DELETE. Demo resets drop and recreate the Postgres volume (scripts/reset-demo-state.sh). |
| 76 | §6 | Acknowledging or resolving an alert requires a passkey session and writes an audit entry; no step-up. |
| 77 | §8 | The overview flags devices that are ACTIVE but have no non-revoked certificate (needs_attention CERT_REVOKED_STATE_ACTIVE), with a "retry quarantine" hint on the dashboard. |
| 78 | §6 | A clinical streak restarts if any batch id in it is no longer ACCEPTED or SIGNAL_DEGRADED, so an alert can never list quarantined evidence. The quarantine CTE still resets streaks only for tainted baselines. |
| 79 | §6 | The clinical evaluation queue is capped (vitalsshield.clinical.queue-capacity, default 1000 per process). Overflow and evaluations lost to a crash stay unevaluated (clinical_evaluated_at NULL), are counted on the dashboard, and are never replayed out of order. A durable evaluation outbox is "Designed". |
| 80 | §1, §8 | Manual Touch ID verification (2026-11-16, MacBook, Chrome) confirmed passkey registration with the setup code, a Touch ID provisioning approval that passed Protocol A re-verification (dev_touchid_001 enrolled at boot_epoch 1), and a Touch ID step-up quarantine that refused the device's reconnect at the handshake. Discoverable sign-in after sign-out, the token disappearing after reload, and repeat sign-in with sign count 0 are covered by the virtual-authenticator runs; manual confirmation is pending. |
| 81 | §4 | Protocol B binding: the request's issuer_key_hash and serial_number must equal the TLS client certificate of the connection (else 403 RENEWAL_CERT_MISMATCH). The HMAC challenge tag covers the purpose, issued_at_ms, the nonce, and that serial. The HMAC key is 32 random bytes generated in memory at each boot. |
| 82 | §4, §6 | The global lock order gains certificates: devices -> certificates -> telemetry_records -> patient_device_assignments -> clinical_alerts -> audit advisory lock last. |
| 83 | §3, §4 | Renewal is due at 2/3 of the leaf's validity (not_before to not_after) in every profile; production 12 h renews at 8 h. The demo/local leaf TTL is PT4M, because notBefore is backdated 60 s, so a leaf lives about 3 minutes after issuance and renews about every 1m40s. |
| 84 | §4 | When a RENEWED certificate's grace_expires_at passes, its live sockets are closed by a scheduled eviction. A sweeper marks certificates past not_after as EXPIRED and deny-lists them. |
| 85 | §4 | Simulator crash safety: a renewed certificate and its key are persisted as pending before use and promoted to current after the first 200. On restart a valid pending certificate is preferred. A lost renew response leads to another renewal, and the server revokes the unused pending certificate as REPLACED_BEFORE_USE. |
| 86 | §4 | The simulator renews immediately on 409 ASSIGNMENT_CHANGED (spec Protocol B trigger), after storing the new assignment id. |
